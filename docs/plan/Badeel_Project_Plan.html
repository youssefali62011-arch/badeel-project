1. Executive summary

When a medicine is out of stock in Egypt, patients and pharmacists need a product with exactly the same active ingredient, strength and dosage form. Brand names differ, Arabic and English spellings vary, and nothing on the box warns the patient about interactions with their other medicines.

Badeel already solves the core of this. It holds 22,757 Egyptian products linked to 8 open sources. Its exact-alternative engine and spelling-tolerant search work, with 93.0% top-1 accuracy on 18,000 misspelled queries. Each patient gets warnings for interactions, allergies, conditions and look-alike names. Voice search, photo search, reminders and an installable app are built. An automated attack suite blocks all 65 attacks.

This plan splits the remaining work into two semesters:

  • Semester 1 (now – 14 Jan 2027): finish the build. Verify the data with a pharmacist, strengthen the AI search, finish the advanced security features, deploy with HTTPS, then freeze features.
  • Semester 2 (Feb – Jun 2027): prove it and write it up. Run the experiments (gold set, real queries, user study), write thesis chapters 2–7, submit a research paper, and allow only small fixes.
The rule for both semesters: every feature ships with a test and a number. Accuracy, speed, coverage and attack rate are measured by a script in the repository, so every table in the thesis and the paper can be regenerated.

2. The project

Problem

  • Medicine shortages are frequent in Egypt. Choosing an alternative by hand is slow and error-prone: the same ingredient may come at another strength or form, and salts differ (diclofenac sodium vs potassium).
  • Patients search with misspelled names, in Arabic letters for English brands ("اوجمنتين"), or in Franco.
  • Safety information is scattered across international databases that do not use Egyptian brand names.
  • Health data is sensitive, and Egypt's Personal Data Protection Law (No. 151 of 2020) treats it as sensitive data.

Objectives

  1. Find exact alternatives (same ingredient, strength, form) with precision ≥ 0.98, verified against a pharmacist-reviewed gold set.
  2. Find the intended product despite spelling mistakes in Arabic, English and Franco, and from a photo or voice.
  3. Give each patient warnings that apply to them: interactions, allergies, conditions, pregnancy, look-alike names.
  4. Protect health data by design: encryption, access control, tamper-evident logs, tested against real attacks.
  5. Publish a cleaned, linked Egyptian drug dataset as an open benchmark.

3. System architecture

Technology

  • Python 3, Flask (app factory, 7 blueprints), Jinja2, vanilla JavaScript, CSS tokens (dark/light)
  • SQLite today; PostgreSQL for production (Semester 1)
  • scikit-learn (ranker), Tesseract OCR, Web Speech API, Web Push (PWA)
  • gunicorn on Render; PythonAnywhere as a fallback

Security controls in place

  • Strict Content-Security-Policy (no inline script or style), CSRF tokens, rate limits
  • Strong passwords (≥ 15 characters), role checks on every route
  • Health data encrypted with Fernet and stored only with consent
  • Audit log that never names the medicine or condition; security log; trap pages for scanners

How the data is joined

Each source names ingredients its own way. Badeel converts every name to one moiety key: lower case, synonyms unified, salt words removed for matching. The key is then extended with the official RxNorm name (paracetamol → acetaminophen). A source row is kept only when its ingredient is sold in Egypt, which keeps the database small and fast.

The whole pipeline runs with python manage.py collect-data. Every run writes the date and licence of each source to data/raw/…/SOURCE.json and prints a coverage report, so the numbers in this document can be reproduced.

How the new test data is built

  • Gold set (500 pairs). Stratified by single vs combination products, dosage form, and "near misses" (same ingredient, different strength or salt). A pharmacist labels each pair "exact alternative" or "not". 100 pairs are labelled twice to report agreement (Cohen's κ).
  • Dictation study (real queries). Volunteers hear or see 40 drug names each (audio, box photo, handwritten note) and type what they would search. 30 volunteers × 40 names = 1,200 real queries in Arabic, English and Franco. No personal data is kept.
  • Photo set. 200 boxes photographed by the team in normal light, at two angles, with phones of different quality.
  • User study. Five tasks (find an alternative, save a medicine, read a warning, set a reminder, use voice search), then the System Usability Scale. Three groups: patients, pharmacists, adults over 60.
  • Statistics. 95% confidence intervals for proportions; McNemar's test when two models answer the same queries; mean ± standard deviation across cross-validation folds.

10. Research paper plan

Paper A — main paper

Working title: Badeel: Exact Medicine Alternatives with Bilingual Misspelling-Tolerant Search and Personalised Safety Warnings for the Egyptian Market. The final title follows the final product name.

Research questions

  1. RQ1. How accurately can rule-based normalisation identify exact alternatives in a noisy national drug list? (C2)
  2. RQ2. How much does learned ranking improve bilingual misspelled search over a TF-IDF baseline, and how does LightGBM compare? Do results on generated queries hold for real ones? (C3)
  3. RQ3. What coverage and precision do open international sources reach when linked to Egyptian products? (C1, C4)
  4. RQ4. Is the system usable by patients, pharmacists and older adults? (SUS)

Structure (IMRaD, 8–10 pages): introduction, related work, data, method (normalisation, ranking, safety layer), experiments, results, discussion and limitations, conclusion.

Candidate venues (check each call for papers and deadline in January):

  • Journals with rolling submission: JMIR Formative Research; BMC Medical Informatics and Decision Making.
  • IEEE conferences held in Egypt, for example NILES, ITC-Egypt and MIUCC.

Paper B — dataset paper (optional)

The linked Egyptian dataset (C1), submitted to Data in Brief, with the Zenodo DOI. It reuses chapter 5 and the coverage tables.

Paper C — security (optional)

A short paper on security by design for a health web app (C5): the attack suite, the tamper-evident log, blind-index allergy checks, and bot detection with a honeypot.

Writing rules:
  • Every number in the paper comes from a script in checks/, ml/ or manage.py.
  • Tables are generated, not typed.
  • Limitations are stated plainly: generated queries, DrugCentral noise, SIDER age, the U.S. origin of the ISMP list.

Ethics

  • Badeel gives information, not prescriptions. There is no dose calculator, and a ticked danger sign stops all suggestions.
  • Studies with people need university ethics approval, written consent, and anonymous answers.
  • Health data is stored only with consent, encrypted, and can be deleted by the user.

Licences

  • Each dataset file carries the licence of its source.
  • DDInter (non-commercial) and the share-alike sources (DrugCentral, SIDER) limit how the data can be reused. This is stated in the dataset card and the paper.

12. Ways of working

  • One task, one GitHub issue. Each issue has an owner, a "done when" line from this plan, and a link to its pull request.
  • Branches and pull requests for every change. A pull request is merged only when python -m unittest and checks/security_check.py pass.
  • Results files go in docs/results/. They are the source for the thesis and the paper.
  • Data changes run through manage.py commands, so the database can be rebuilt from scratch.
  • This plan is updated at every milestone: statuses, dates, and anything moved to future work.
